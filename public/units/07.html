第7章　エラーを見つけて修正する

7.1 知る：完成した機能を「確かめられる」ようにする

機能が増えると、一つの症状にも複数の原因が考えられます。本章では、問題を思いつきで直さず、症状を再現し、仮説を立て、確かめてから、必要な部分だけを修正する方法を学びます。原因が分からないまま複数のファイルを変えると、結果が変わった理由を追えません。これがデバッグの基本です。

本章では、Node.jsの自動テストとブラウザの開発者ツールを併用します。学習の目標は次の四つです。

  • HTMLの構造、JavaScriptの構文、HTTP通信のどこに問題があるかを切り分ける。
  • test.mjsが何を検査しており、何を検査していないかを説明する。
  • テストをわざと失敗させ、失敗内容から原因を読み取って復元する。
  • 自動テストの結果と、ブラウザで観察した事実を区別して記録する。

大事なのは、最初からすべてのエラーを解決できることではありません。確認できたことと、まだ確かめていないことを分けられることです。

7.3 読み解く：今回使用するファイルと自動テスト

test.mjsはNode.jsで動くテスト用ファイルです。.mjsはECMAScriptモジュールとして扱う拡張子で、ブラウザ画面を作るものではありません。

テストを実行するには、少なくとも次のファイルが同じ07-debugフォルダーに必要です。

07-debug/
├─ index.html       ← HTMLのタブ・パネルを検査
├─ app.js           ← 構文を検査
├─ style.css        ← ブラウザでの表示に使用
├─ server.mjs       ← 構文とHTTP応答を検査
└─ test.mjs         ← 今回読む自動テスト

index.htmlとapp.jsは第6章で使ったものを引き継ぎます。

node --test test.mjs

--testはNode.jsのテストランナーを使用する指定です。テストランナーは、登録された確認処理を実行し、成功・失敗をまとめて表示します。教材のtest.mjsには三つのテストがあり、それぞれが独立した役割を持っています。

テスト名（要約）確認する内容確認しない内容
タブとパネルの対応特定のidとaria-controlsの個数・文字列の一致実際のクリック動作、表示、重複IDの完全な検出
JavaScriptの構文app.jsとserver.mjsが構文として解釈できるか実行時の例外や画面操作の正しさ
APIキー未設定時の応答/が200、/api/newsが503、指定した秘密ファイルのパスが404GNewsへの実接続、APIキーを設定した場合の成功、すべてのURLの安全性

テストがすべて成功したことと、Webアプリのあらゆる動作が正しいことは同一ではないことを留意しましょう。

7.4 読み解く：テストを書くための基本部品

test.mjsの冒頭には、次の読み込みがあります。

import test from 'node:test';
import assert from 'node:assert/strict';
import { readFile } from 'node:fs/promises';
import { spawn, spawnSync } from 'node:child_process';
import { join, dirname } from 'node:path';
import { fileURLToPath } from 'node:url';

const folder = dirname(fileURLToPath(import.meta.url));

importで機能を読み込みます。node:testはテスト、node:assert/strictは期待値の検証、readFileはファイルの読み込み、spawn・spawnSyncは別プログラムの起動に使います。

folderはtest.mjsのあるフォルダーを指し、index.htmlなどの参照先を定めます。サーバー起動時にもcwd: folderを指定します。

7.5 読み解く：HTMLの対応関係を自動で調べる

最初のテストは、タブとパネルの対応を調べます。

test('タブ数とパネル数が一致し、aria-controlsが対応する', async () => {
  const html = await readFile(join(folder, 'index.html'), 'utf8');
  const ids = [...html.matchAll(/id="(panel-[^"]+)"/g)].map(m => m[1]);
  const controls = [...html.matchAll(/aria-controls="(panel-[^"]+)"/g)].map(m => m[1]);
  assert.equal(ids.length, controls.length);
  assert.deepEqual(ids.sort(), controls.sort());
});

第4章で学んだように、タブのaria-controls="panel-news"は、id="panel-news"のパネルを指します。もし名前が違えば、JavaScriptが意図するパネルを探せなくなる可能性があります。そこで、このテストはHTMLファイルを文字列として読み込み、二つの名前の集まりを比較します。

matchAllで正規表現に一致するidとaria-controlsを集めます。assert.equalは件数、assert.deepEqualは並び替え後の値を比較します。

たとえば、ニュースタブのaria-controlsだけをpanel-news-typoに変更すれば、パネル側のidにはその名前が存在しないため、比較結果が一致しなくなります。ただし、このテストはHTMLをDOMとして解析していません。特定の書き方を正規表現で調べる簡易テストです。

7.6 読み解く：JavaScriptの構文を確認する

二番目のテストは、JavaScriptの構文エラーを見つけるためのものです。構文エラーとは、括弧が閉じられていないなど、言語の書き方として解釈できない問題です。

test('JavaScriptファイルに構文エラーがない', () => {
  for (const filename of ['app.js', 'server.mjs']) {
    const result = spawnSync(
      process.execPath,
      ['--check', join(folder, filename)],
      { encoding: 'utf8' }
    );
    assert.equal(result.status, 0, result.stderr);
  }
});

for...ofでファイルを順に調べ、spawnSyncでnode --checkを実行します。--checkはプログラムを動かさず構文だけを検査します。

result.statusが0なら、コマンドは正常終了したと判断して次へ進みます。0以外であれば、assert.equalが失敗し、エラーの詳細がテスト結果に表示されます。result.stderrは、コマンドがエラー内容などを書き出すための出力です。

node --checkでわかるのは構文の誤りだけです。正しい動作は実行して別途確かめる必要があります。

7.7 読み解く：サーバーを起動し、HTTP応答を検査する

三番目のテストは、自分のNode.jsサーバーを一時的に起動し、実際にHTTPリクエストを送ります。HTTPは、ブラウザとサーバーが情報をやり取りするときの規則です。サーバーは処理結果を200や503などのステータスコードで返します。

最初に、テストがサーバーを起動する部分を見ます。

test('APIキー未設定ならニュースAPIは503で、秘密ファイルは配信しない', async () => {
  const child = spawn(process.execPath, ['server.mjs'], {
    cwd: folder,
    env: { ...process.env, GNEWS_API_KEY: '', PORT: '0' },
    stdio: ['ignore', 'pipe', 'pipe']
  });
  // 以下にサーバーへの確認と終了処理が続く（省略）
});

spawnでサーバーを起動します。cwdは作業場所、envはテスト用の環境変数、PORT: '0'はOSによる空きポートの選択です。

このテストは、通常のニュース取得が成功するかどうかを調べるものではありません。APIキーが設定されていない場合に、サーバーが想定どおりの失敗を返すかを確認します。server.mjsには次の条件があります。

async function news(reqUrl, res) {
  const keyword = reqUrl.searchParams.get('keyword') || 'テクノロジー';
  if (!keywords.has(keyword)) return json(res, 400, { error: '未対応のジャンルです。' });
  if (!apiKey) return json(res, 503, { error: 'GNEWS_API_KEY が未設定です。.env を確認してください。' });
  // 以下は省略
}

この教材では、キーが空ならGNewsへ問い合わせる前に503を返す設計です。HTTPの一般的な意味として503はサービスがリクエストに対応できない状態を示しますが、キー未設定を503で表現することは教材サーバーの実装上の判断です。すべてのWeb APIが同じ条件で503を返すわけではありません。

テストの応答確認部分では、次の処理が実行されます。

const html = await fetch(url);
assert.equal(html.status, 200);
const news = await fetch(url + '/api/news');
assert.equal(news.status, 503);
assert.match((await news.json()).error, /GNEWS_API_KEY/);
for (const path of ['/server.mjs', '/.env', '/.env.example']) {
  assert.equal((await fetch(url + path)).status, 404);
}

fetchで/の200、ニュースAPIの503、対象パスの404を確認します。assert.matchでエラーメッセージにGNEWS_API_KEYが含まれるか検査します。

server.mjsはstaticFilesの登録対象のみ配信します。/.envと/server.mjsの404を確認しますが、この結果だけで安全性全体は保証できません。

なお、三番目のテストの終わりではfinallyを使い、成功・失敗にかかわらず起動したサーバープロセスにchild.kill()を呼びます。テスト用のサーバーを起動したままにしないための処理です。tryとfinallyは、途中でエラーがあっても後始末を実行するために使います。

7.8 読み解く：テストの成功・失敗を読む

テストランナーが表示する結果では、okが成功、not okが失敗を表します。三つのテストが成功したときは、概ね次のような表示になります。これは表示形式を説明するための例であり、実行時間などは環境によって異なります。

TAP version 13
# Subtest: タブ数とパネル数が一致し、aria-controlsが対応する
ok 1 - タブ数とパネル数が一致し、aria-controlsが対応する
# Subtest: JavaScriptファイルに構文エラーがない
ok 2 - JavaScriptファイルに構文エラーがない
# Subtest: APIキー未設定ならニュースAPIは503で、秘密ファイルは配信しない
ok 3 - APIキー未設定ならニュースAPIは503で、秘密ファイルは配信しない
1..3
# tests 3
# pass 3
# fail 0

TAPはテスト結果の表示形式です。passは成功数、failは失敗数。not okの項目で期待値と実際の値を比べましょう。

7.9 試す：意図的にHTMLを壊し、修正する

まず、自動テストが問題を見つける様子を確かめます。変更対象は一か所だけです。作業前にファイルのコピーを保存してもかまいません。

  1. 変更前を確認する：node --test test.mjsを実行し、三つのテストが成功することを確かめます。
  2. 予測する：ニュースタブのaria-controlsが存在しないパネル名を指したら、何番目のテストが失敗するか記録します。
  3. 一か所だけ変更する：index.htmlのaria-controls="panel-news"をaria-controls="panel-news-typo"へ変更します。パネル側のid="panel-news"は変更しません。
  4. 結果を確認する：再度node --test test.mjsを実行し、not okになったテスト名と、表示された二つの配列の違いを書き留めます。
  5. 理由を説明する：テストが「値の個数」ではなく「値の一致」で失敗した理由を、assert.deepEqualの行と結び付けて説明します。
  6. 元に戻す：aria-controls="panel-news"へ戻し、同じコマンドを実行して成功することを確かめます。

この実験では、HTMLを壊しても構文テストは成功する場合があります。テストが別々の条件を調べているからです。失敗を一つ作っただけで、三つすべてが同時に失敗するわけではない点にも注目してください。

7.10 試す：構文エラーと実行時の問題を区別する

次は、JavaScriptの構文検査が何を見つけるかを確かめます。ここでも変更は一か所に限定します。

  1. 変更前を確認する：node --check app.jsを実行し、正常終了することを確かめます。
  2. 予測する：ファイルの末尾に閉じられていない括弧があったら、何が起こるかを予測します。
  3. 一か所だけ変更する：app.jsの末尾に、次の意図的に不完全な一行を追加します。これは動作するコード例ではありません。
   function broken( {
  1. 結果を確認する：node --check app.jsとnode --test test.mjsを順に実行し、SyntaxErrorなどのメッセージと、失敗するテストの名前を確認します。
  2. 理由を説明する：構文として解釈できないため、タブやニュースの動作を調べる段階まで進めないことを説明します。
  3. 元に戻す：追加した一行を完全に削除し、構文検査と三つのテストが再び成功することを確認します。

構文検査が成功した場合でも、ブラウザ上の動作まで保証されません。たとえばidの書き間違いによるnullの扱いは、実行したときに初めて問題になることがあります。その場合には、次節の開発者ツールを使います。

7.11 試す：開発者ツールのElementsとConsoleを使う

ブラウザの開発者ツールは、表示されているページの要素や、JavaScriptのエラー、通信内容などを確認するための道具です。Chromium系ブラウザでは主にElements、Console、Networkなどの名前で表示されます。ブラウザによって名称や配置は異なります。

Elementsでtab-newsとpanel-newsのaria-selected・hiddenを確認します。状態が正しければ、次はCSSを調べます。

.filetab[aria-selected="true"] {
  background: var(--surface);
  border-color: var(--border);
  color: var(--text);
}

この規則は、タブの選択状態を見た目に反映する部分です。選択状態が更新されない問題と、選択状態は変わるのに色が変わらない問題では、調べる場所が異なります。

Consoleでは、JavaScriptのエラーメッセージを確認したり、式を入力したりできます。次の式は説明のための確認用であり、app.jsに追加する必要はありません。

document.querySelectorAll('[role="tab"]').length
// この教材では通常 2

document.getElementById('tab-news').getAttribute('aria-controls')
// 通常 "panel-news"

document.getElementById('panel-news') !== null
// 通常 true

SyntaxErrorが表示されたらコードの書き方を調べます。一方、TypeErrorのような実行中の例外が出た場合は、エラーの前後で取得した要素が存在していたか、操作する値が想定どおりかを調べます。最初に出たエラーを記録するのは、後から発生したエラーが、その影響で起きている可能性があるためです。

7.12 試す：Networkで通信の失敗を読み取る

ニュースの通信を調べるときはローカルサーバーを起動し、http://127.0.0.1:3000/を開きます。file://では/api/newsを正しく試せません。

APIキー未設定時の動作を安全に確認する場合は、教材フォルダーに.envを用意し、少なくとも次のようにキーの値を空欄にします。実際のAPIキーを本文や実験記録に貼り付ける必要はありません。

GNEWS_API_KEY=
PORT=3000

Node.js 20.6以上の環境では、次のコマンドで起動できます。

node --env-file=.env server.mjs

環境変数がすでに別の場所で設定されている場合は、.envの値だけで上書きされるとは限らないため注意してください。キーが確実に空であることを試す自動テストでは、前述のようにテスト用プロセスのenvを明示的に指定しています。

Networkで/api/news?keyword=...の応答を確認します。キーが空なら503とGNEWS_API_KEYを含むエラーになり、画面は取得失敗を表示します。

503という番号だけで原因は決まりません。応答メッセージも確認しましょう。キー未設定時はGNewsへ通信せずにサーバーが応答します。

なお、教材のapp.jsにはnewsStartedという変数があり、ニュースを初めて開いたときだけloadNews()を実行します。一度エラーになっても、タブを往復するだけでは再度取得しません。

7.13 考える：キャッシュはどこに保存されているか

ニュースが前と同じ内容に見えるとき、キャッシュの影響を疑うことがあります。キャッシュとは、取得や計算を繰り返さずに済むよう、以前の結果を一時的に保持する仕組みです。ただし、どこに保存するかは実装によって異なります。

本教材のserver.mjsには、次のコードがあります。

const ttlMs = 5 * 60 * 1000;
const cache = new Map();

ニュースのキャッシュはサーバーのMapにあり、ブラウザのApplicationでは直接見られません。server.mjsとNetworkのcache値で確認します。成功した取得がない場合は検証できません。

また、server.mjsのAPI応答にはCache-Control: no-storeが設定されています。これはブラウザなどに対するHTTPキャッシュの指定であり、サーバーのメモリ内にあるMapとは別の仕組みです。同じ「キャッシュ」という名前でも、場所と目的を確かめる必要があります。

7.14 考える：自動テストで確認できないことを見極める

自動テストは、繰り返し確かめたい条件を一定の方法で検査できる点が強みです。今回のテストは、HTMLの一部の対応、JavaScriptの構文、キー未設定時のサーバー応答という、外部サービスに頼らず確認しやすい条件を選んでいます。この範囲であれば、修正後に同じコマンドを再実行し、以前の条件が維持されているかを調べられます。

新しい機能を追加したときは、まず「何ができれば成功なのか」を具体的に書き出してみてください。自動化するかどうかは、その条件を繰り返し確認する必要があるか、結果をプログラムで判定できるかによって考えます。目で確かめたこと、テストによって判定したこと、外部条件のため未検証のことを、同じ「確認済み」とまとめないことが大切です。

7.16 ふりかえり：確認の結果を根拠に直す

本章では、エラーを再現し、仮説を確かめ、修正後に再検証する方法を学びました。test.mjs・Elements・Console・Networkは、それぞれ異なる問題を調べる道具です。

これまでの章では、機能を一つずつ作り、その動作を確かめてきました。ここで身につけたデバッグの手順は、今後新しい機能を加えるときや、制作物を見直すときにも役立ちます。「動いたかどうか」だけでなく、「どの条件を、どの根拠で確認できたか」を説明できることが、自分で学び続けるための土台になります。
