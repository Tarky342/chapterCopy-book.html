# ビジュアル・スタイルガイド v2（読者の理解を最優先）

## 視覚表現の優先順位

1. **実際のアプリ画面を使う**：既知の見た目を入口にする。画面の一か所を囲む、必要な部分だけ拡大する。
2. **画面とコードを結ぶ**：コードの全文ではなく、該当する短い箇所だけ示す。
3. **操作前後を比べる**：動きを説明する際は「何をした→何が変わった」を示す。
4. **抽象図・比喩・写真**：上の方法で説明できないときだけ使う。比喩を実際の実装と混同させない。

## 見た目の基本

- 一枚につき一つの問い。主役を明確にし、**最初に描かない要素を決める**。
- 図中の文字を増やすより、キャプションで補う。新しい専門語は最大1つ。
- 1〜4の焦点要素、ラベル最大4つ。実際は少ないほどよい。
- 同じ部品は章をまたいで同じ形・色で表す。色だけで意味を伝えない。
- 白または透明の背景を初期案とする。図は編集可能なSVG、実画面はPNGを基本候補にする。
- 幅640px相当と白黒でも主要な情報を読めるようにする。表示先に合わせて比率を決める。
- 実画面のスクリーンショットは対象章の動作から取得する。個人情報、APIキー、第三者のニュース本文を写さない。
- 写真・イラストは雰囲気づくりだけのために依頼しない。第三者の素材は権利を確認する。

## 制作者への依頼文の順序

1. 読者が困っていること（1文）
2. 一目で伝えること（1文）
3. 描くもの（最大4要素）
4. 描かないもの（最低1つ）
5. 参照する実画面・実コード
6. 形式と納品先、確認方法

色・フォント・線幅などの詳細指定は、読者の理解に必要な場合と、ユーザーがスタイルを確定した場合だけにする。制作の自由度を不必要に奪わない。
